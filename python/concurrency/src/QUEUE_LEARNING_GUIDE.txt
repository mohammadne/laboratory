YOUR QUESTION:
═════════════
"The consumer is blocking and waiting for item, how does t2.join() pass?"

ANSWER IN ONE SENTENCE:
═════════════════════════════════════════════════════════════════════════════
Blocking doesn't mean stuck - it means the thread pauses efficiently,
wakes up when data arrives, and can then exit normally.
═════════════════════════════════════════════════════════════════════════════


KEY CONCEPT: Blocking ≠ Stuck Forever
═════════════════════════════════════════════════════════════════════════════

❌ WRONG:  "queue.get() blocks = thread hangs forever"
✓  RIGHT:  "queue.get() blocks = thread waits for data efficiently"

When queue.get() is called on an empty queue:
  1. Thread pauses (blocks)
  2. Thread does NOT consume CPU
  3. OS keeps thread in "waiting" state
  4. When producer puts an item:
     └─ OS wakes thread automatically
     └─ Thread continues from queue.get()
  5. Thread gets the item and continues


HOW t2.join() SUCCEEDS:
═════════════════════════════════════════════════════════════════════════════

t2.join() means: "Wait for thread t2 to finish"

Flow:
  1. Consumer thread calls queue.get() repeatedly
  2. Sometimes it blocks (queue empty), sometimes it gets item
  3. After getting 5 items, consumer's for loop ends
  4. Consumer thread function returns
  5. Thread exits and terminates
  6. t2.join() returns because thread has exited

The blocking doesn't prevent thread from exiting!

THE CORE MECHANISM:
═════════════════════════════════════════════════════════════════════════════

Queue Internal State:
  - items: [job1, job2, job3, ...]
  - blocked_getters: [Thread1, Thread2, ...]  ← threads waiting on get()

When thread calls queue.get():
  IF items is NOT empty:
    ✓ Remove first item from items
    ✓ Return it immediately
    └─ Thread continues
  ELSE (items is empty):
    ✓ Add thread to blocked_getters list
    ✓ Thread goes to sleep (OS manages this)
    ✓ Thread waits here...
       (NOT consuming CPU!)

When thread calls queue.put(item):
  ✓ Add item to items list
  IF blocked_getters is NOT empty:
    ✓ Remove first thread from blocked_getters
    ✓ Wake it up (OS wakes it)
    ✓ That thread resumes from queue.get()
    └─ It gets the item!


WHY QUEUE.GET() IS EFFICIENT:
═════════════════════════════════════════════════════════════════════════════

❌ BAD (Busy-waiting):
   while True:
       if queue.has_items():
           get_item()
           break
       time.sleep(0.001)  # Wastes CPU checking 1000x per second!

✓  GOOD (Queue blocking):
   job = queue.get()      # Block efficiently
                          # OS wakes when ready
                          # Zero CPU wasted

QUIZ - Test Your Understanding:
═════════════════════════════════════════════════════════════════════════════

Q1: What happens when consumer calls queue.get() on an empty queue?
A1: Thread blocks (pauses), waiting for item. Doesn't consume CPU.

Q2: How does the blocked thread wake up?
A2: When producer calls queue.put(), OS automatically wakes blocked thread.

Q3: Does blocking prevent thread from exiting?
A3: No! Thread can exit. It just means "pause here until data arrives".

Q4: Why can t2.join() return if consumer might be blocked?
A4: Because after getting all items, consumer loop ends, thread exits.
    Then join() returns.

Q5: Why is queue.get() better than busy-waiting?
A5: Queue uses OS synchronization (Condition Variable).
    Thread blocks without consuming CPU.
    Thread wakes EXACTLY when needed.


ADVANCED: What Actually Happens:
═════════════════════════════════════════════════════════════════════════════

Under the hood, Python's Queue uses:
  - Mutex (Lock) for thread safety
  - Condition Variable for efficient blocking/waking

Condition Variable mechanism:
  1. Thread calls queue.get()
  2. Queue acquires lock
  3. Queue checks if items available
  4. If not: thread calls condition_var.wait()
     └─ Lock is released
     └─ Thread goes to sleep (OS efficiently)
     └─ Thread waits...
  5. When producer puts item:
     └─ Producer acquires lock
     └─ Adds item to queue
     └─ Calls condition_var.notify()
     └─ OS wakes one waiting thread
  6. Woken thread acquires lock again
  7. Thread gets item and continues
  8. Thread releases lock


COMMON MISTAKES:
═════════════════════════════════════════════════════════════════════════════

❌ Thinking blocking = hung thread
   └─ Actually: efficient OS-managed pause

❌ Thinking join() waits for active thread
   └─ Actually: join() waits for thread to exit

❌ Using busy-waiting instead of blocking
   └─ Actually: queue.get() handles it efficiently

❌ Creating your own queue without threading primitives
   └─ Actually: use threading.Queue or asyncio.Queue


SUMMARY:
═════════════════════════════════════════════════════════════════════════════

1. queue.get() blocks when empty
   └─ Thread pauses, doesn't consume CPU

2. Producer puts item
   └─ Blocked consumer is woken up

3. Consumer resumes from get() with item
   └─ Processes it

4. After all items consumed
   └─ Consumer loop ends, thread exits

5. t2.join() returns
   └─ Thread has exited!

This is elegant, efficient, and thread-safe!
